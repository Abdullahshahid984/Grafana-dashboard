## 1. Confirm the pod is healthy
```powershell
kubectl get pods -n api-cims-v1
```

## 2. Show the credential is empty in the pod's environment
```powershell
kubectl exec -it api-cims-56fbf694d6-5gfq9 -n api-cims-v1 -c api-cims -- sh -c 'echo "KANA:$KANA_API_AUTHORIZATION_KEY:END"'
```

## 3. Show the same value IS present in the CSI-mounted file
```powershell
kubectl exec -it api-cims-56fbf694d6-5gfq9 -n api-cims-v1 -c api-cims -- sh -c 'wc -c < /mnt/kvadscusprdihub01-secrets/KANA-API-AUTHORIZATION-KEY'
```

## 4. Show the same value IS present in the Kubernetes Secret object
```powershell
kubectl get secret kvadscusprdihub01-secrets-syncd -n api-cims-v1 -o jsonpath='{.data.KANA_API_AUTHORIZATION_KEY}' | Measure-Object -Character
```

## 5. Show other secrets in the SAME pod work fine (rules out a broad sync issue)
```powershell
kubectl exec -it api-cims-56fbf694d6-5gfq9 -n api-cims-v1 -c api-cims -- sh -c 'echo "CLIENTID:$CIMS_CLIENTID:END"; echo "CLIENTSECRET:$CIMS_CLIENTSECRET:END"'
```

## 6. Show a DIFFERENT app, using the SAME Key Vault, also works fine (rules out Key Vault/CSI-wide issue)
```powershell
kubectl exec -it api-accountlookup-6b48549955-k54ch -n api-accountlookup-v1 -c api-accountlookup -- sh -c 'echo "OKTA:$EI_OKTA_AUTHORIZATION:END"'
```

## 7. Confirm this secret is only referenced by api-cims cluster-wide (fully isolated)
```powershell
kubectl get secretproviderclass -A -o yaml | Select-String -Pattern "KANA" -Context 3,3
```

## 8. Confirm SecretProviderClass mapping itself is correctly configured (rules out a naming typo)
```powershell
kubectl get secretproviderclass -n api-cims-v1 -o yaml | Select-String -Pattern "KANA" -Context 5,5
```
