## 2. Production Latency Investigation (api-rewards-v1)

- Supported the investigation into unexplained delay between APIM and the service in production, by correlating App Insights, APIM gateway logs, Container Insights and Prometheus data per pod.
- The data showed the delay came from inside the older pods (heavy JVM garbage collection and CPU throttling), not from the network or APIM. It dropped to near zero after the redeploy.
- Recommended weekly overnight pod recycles as a safety net, and flagged an ingress gateway HPA that reads "at max" and a failing navigation link operation on the ext APIM subnet to the owning team.

## 3. AKS Backup and Restore (Infrastructure as Code)

**Early build (March to May)**

- Raised the GSR for storage account private endpoints scoped to the AKS subnets.

**Restore validation**
- Validated the first end-to-end restore of `api-customerlookup-v1` from DEV to POC-02. It needed KEDA on POC-02, an Azure Policy update to allow DEV ACR images, a federated credential for the POC-02 OIDC issuer and AcrPull for the POC kubelet identity. Pods came up 2/2 Running, which proved the process before I scaled it out.
- Resolved KEDA ScaledObject conflicts, Workload Identity OIDC issuer mismatches, CSI Secret Store failures, ACR pull gaps and Istio revision mismatches. I added KEDA to POC-02 so restored ScaledObjects could reconcile, which cleared the `FailedGetExternalMetric` errors.

I validated it with a full restore of all 71 namespaces from DEV to POC-02, with credentials created for every workload and zero 401 errors, before moving to the DEV restore cluster. It removed all manual intervention and is reusable for future DR targets.

**Restore cluster coexistence (dev-rst)**
- When I set up the dev-rst cluster, it initially revoked RBAC and federated credentials from the original dev cluster, its app alerts clashed with the original cluster's alerts in the same resource group, and the Terraform Cloud workspace for rst couldn't be found.
- I fixed the workload onboarding code so both clusters keep their own RBAC and federated credentials, the rst cluster uses the original environment's workspace, and rst workload alerts are skipped to avoid name clashes. The fix was deployed in workload onboarding build 274 and verified on both clusters.
- I resolved a Prometheus rule group conflict on the restore cluster by importing the existing rule group into Terraform state, then added an exclusion list so restore clusters never get duplicate alert rule groups.
- I moved restore validation to POC-02 to protect the shared DEV environment, and wrote updates for the team and the application teams. I made clear that RBAC was the only issue caused by the backup work.

**Fixes found along the way**

The Terraform referenced a module output that didn't exist, so the Contributor role on the snapshot resource group was never created. I added a data source lookup for the cluster identity without touching the shared module outputs.

## Lessons Learned

- Early PR feedback on the backup work showed I needed to verify existing cluster resources before implementing. I now check what is actually running across environments first.
- My first restore cluster attempt in the shared DEV environment caused RBAC and pipeline conflicts for teammates and application teams. I fixed it the same day, moved validation to POC-02, and now I validate shared module changes across environments before raising PRs.
- Terraform orders resources by references, not names. I check for plain-string dependencies in reviews.
- Manual changes get reverted. When a change is made by hand (such as the APIM operation), I add it to code so the pipeline doesn't undo it.
- Evidence beats assumption: several of my early hypotheses were disproved by logs and deployment history. I verify first and separate confirmed facts from assumptions.
- Taking on a new area like APIM shows how much depends on a clear handover, so I document as I go.
