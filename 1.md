Subject: AKS Backup/Restore + Wiz Broker Updates - What's Actually Related

Hey team, wanted to give a quick update on the AKS backup/restore situation since I know there's some confusion about what actually caused what.

I has been setting up a restore/validation cluster (dev-rst) using Azure Backup, so I can actually test and validate that our AKS backups restore correctly and are usable, without touching or risking the original dev cluster in the process. While getting this working, it started causing an RBAC issue on the original dev cluster. Role assignments and federated credentials were getting messed up because the pipeline was treating the restore cluster like it needed its own full run, and it ended up fighting with the original cluster over the same Terraform state. Basically every time it ran, it would touch the original cluster's stuff too. I dug into it, found the root cause, and fixed it the same day. Now the original cluster runs completely untouched like before, and the restore cluster just gets the one extra credential it actually needs to authenticate its restored pods, nothing else gets recreated or touched. I also fixed the alert naming so the two clusters don't clash on alert names either. This part was genuinely caused by the backup/restore setup, and it's sorted now.

While I was fixing this RBAC issue in dev, I was running the workload onboarding pipeline from my feature branch to test and validate my changes, so you will see a few failed pipeline runs in the history from that, don't worry about those. Build number 274 in the workload onboarding release is the successful one that deployed and fixed the issue.

I have restored this on the RST cluster and everything is working fine there. I'm still closely monitoring the original dev cluster, the RST cluster, and the workload onboarding pipeline to make sure this isn't causing any other issues, and so far everything's fine.

One more thing Sahil flagged an incident about the Wiz Broker disconnecting on the dev-rst cluster. I checked it out and the pod is running fine and Wiz is connected, so there's no actual issue there. Flagging it just so you're aware it came up, but it looks like it was just a transient blip on the test cluster, nothing that needed a fix.

So to be clear, only the RBAC issue was actually caused by the backup setup, and that's fixed. The Wiz Broker alert turned out to be a non-issue on closer look. Nothing else points back to AKS backup itself beyond the one RBAC fix.

I have created a PR with these changes, please take a look whenever you get a chance. Suggestions are welcome. 

Summary of what changed:

- The restore cluster is no longer processed as its own cluster in the pipeline - it's now detected automatically from config and handled as an addition to the original cluster's own run, instead of a separate one.
- Removed the logic that was renaming/suffixing the original cluster's RBAC and federated credentials - those are back to being created exactly as before.
- The restore cluster still gets what it needs (its own federated credential) through the existing mechanism the module already had for additional clusters.
- Fixed alert rule naming so it's checked per-cluster instead of one flag for everything, so original and restore cluster alerts don't collide.
- Simplified the Phase 2 pipeline script back to normal, no special-case workspace routing for the restore cluster.
