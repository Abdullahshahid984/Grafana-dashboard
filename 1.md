**Situation:**
In AKS, a pod (`api-cims`) uses `envFrom` to bulk-import all keys from a Kubernetes Secret synced via the CSI Secrets Store driver from an Azure Key Vault into its container's environment variables.

One specific key, `KANA_API_AUTHORIZATION_KEY`, is confirmed present with real content at every upstream layer:
- **Key Vault secret itself** confirmed valid, since a separate Azure App Service uses this exact same secret successfully
- **CSI-mounted file in the pod** 40 characters of real content
- **Kubernetes Secret object** 56 base64 characters, decodable to real content

But this same key reads as **empty (0 characters)** when checked as an environment variable inside the running pod  while every other key in that same Secret object populates correctly, in this pod and in a separate pod/application using the identical mechanism.

This env var is confirmed (code-level) to be what builds the Authorization header for calls to `kanasmc.alldata.net`  so its being empty directly explains the 401 Unauthorized error observed on that call.

**Question:**
Why would one specific key in an `envFrom`-populated Secret fail to appear as an environment variable while every other key populates correctly when both the file mount and the Secret object confirm the data is genuinely present?

Is this most likely a **stale pod snapshot** (environment variables are set once at container startup, and this key's value may not have been fully synced at that exact moment) fixable by a pod restart  or is there a more **structural** Kubernetes/Helm/CSI-driver explanation that a restart wouldn't fix?

**Also:** if this is confirmed as a Kubernetes/CSI-driver-level issue rather than an application code issue, which team would typically own the fix platform/infrastructure (Kubernetes, Helm chart, CSI driver config) or the application development team (deployment manifest, secret references in code)?
