I have been working on AKS backup and restore validation as part of our platform resilience initiative. The goal was to validate that workloads can be successfully restored from a DEV cluster backup and brought back to a running state on a separate restore target cluster. Here is the full journey of what I did, what went wrong, and what I learned.

**Phase 1: Setting up the RST cluster in DEV (same RG)**

I started by creating a dedicated restore cluster (`aks-bfhaks-ihub-eus2-dev-rst-01`) in the DEV environment via the bfhaksplatform Terraform pipeline. The cluster was added to `conf.yaml` along with backup extension, backup instance, cert-manager, Istio ingress gateway, KEDA, Wiz connector and CrowdStrike entries. The idea was to keep it simple same environment, same resource group (`rg-bfhaks-ihub-eus2-dev-01`), restore from DEV backup and validate.

**Phase 2: First restore attempt and blockers**

The restore completed but with warnings. When I ran `kubectl get pods` on the RST cluster all pods were stuck in Init state. Running `kubectl get events` revealed two major issues:

First KEDA ScaledObject conflict. The KEDA admission webhook rejected restore operations because an existing HPA was already managing the same deployment as the ScaledObject being restored. Fix was to delete the conflicting HPAs before retrying the restore.

Second Workload Identity OIDC issuer mismatch (`AADSTS700211`). Each AKS cluster has a unique OIDC issuer URL. The Managed Identity federated credentials on each workload MI only covered the original DEV cluster's OIDC issuer. When pods ran on the RST cluster, Entra ID rejected the token exchange causing the CSI Secret Store to fail mounting Key Vault secrets. All 71 namespace pods were stuck.

**Phase 3: Terraform solution attempts and pipeline conflicts**

To fix the OIDC issue at scale I added Terraform code to the workload onboarding pipeline a `restore_clusters` variable and `workload_identity_restore` resource to automatically create federated credentials for the RST cluster across all 71 workloads. This is where things got complicated.

Adding the RST cluster to `conf.yaml` under `aks_cluster` caused the `app_alerts` module in Phase 01 to create Prometheus alert rule groups for every workload on the RST cluster. Azure Backup had already restored those same rule groups into the same DEV resource group with identical names. When Terraform tried to create them again Azure rejected it with `resource already exists` error breaking the shared DEV pipeline completely and affecting other teams' deployments.

I tried multiple fixes adding `excluded_cluster_names` logic to skip Prometheus rule group creation for RST, `terraform state rm` to remove conflicting resources, manual deletion of rule groups from Azure. Each fix introduced new issues. The `excluded_cluster_names` local was resolving as `known after apply` at plan time so the filter had no effect. Multiple Terraform state conflicts required manual `state rm` operations via WSL. The workspace state lock was triggered multiple times. Other teams' pipelines started failing because they were running on older code versions that still had RST cluster references.

After multiple PRs, state fixes, workspace lock issues and pipeline disruptions the RST cluster approach was abandoned. The shared DEV resource group and shared Terraform pipeline made it too risky.

**Phase 4: Switching to POC-02 (different RG)**

I evaluated using `aks-bfhaks-ihub-eus2-poc-02` as the restore target. It was already running, had its own separate resource group (`rg-bfhaks-ihub-poc-eus2-dev-01`), I had full access, and it sat in the same subscription so Azure Backup restore was possible.

The different RG eliminated the Prometheus conflict completely - restored resources landed in the POC RG, completely isolated from DEV Terraform managed resources. No naming conflicts, no pipeline breakage, no impact on other teams.

**Phase 5: POC-02 restore and additional blockers**

Restoring to a different RG cluster introduced more requirements compared to same RG restore:

Same RG restore (DEV to RST in DEV RG) only one additional requirement: add federated credentials on the source workload Managed Identities for the restore cluster OIDC issuer. That is it, because the restore cluster lives in the same `conf.yaml` so KEDA, Istio and everything else is already installed.

Different RG restore (DEV to POC-02) - more steps needed:
- Istio latest revision must be installed on POC-02 and namespace labels updated to match (`asm-1-28`)
- Azure Policy: POC-02 allowed registries policy must include the DEV ACR (`acrbfhaksihubeus2dev02`) to allow image pulls without this Gatekeeper blocks pod creation
- ACR pull access: POC-02 kubelet identity needs `AcrPull` role on the DEV ACR
- KEDA IAM role: KEDA was not installed on POC-02 - added to conf.yaml and ran bfhaksplatform pipeline
- OIDC access: federated credentials must be added on each workload Managed Identity for the POC-02 OIDC issuer

**Phase 6: Successful validation**

After resolving all blockers, I successfully restored 5 to 6 namespaces from DEV to POC-02. Pods came up in `2/2 Running` state with Key Vault secrets mounting correctly and Workload Identity working. The backup and restore process is validated end to end.

**Current status and remaining gap**

The only remaining gap is automation of the federated credential step. Currently every namespace requires manually adding a federated credential on the workload MI via the portal. With 71 namespaces this is not scalable. I have built the Terraform code (`additional_clusters` variable in the workload onboarding pipeline) and also explored a PowerShell script approach both are being researched for the cleanest implementation.
