I have completed the AKS backup and restore validation on POC-02. I restored 5 to 6 namespaces from the DEV cluster and pods came up successfully with Key Vault secrets mounting correctly.

**Background why POC-02 and not a dedicated RST cluster**

Initially we created a dedicated restore cluster (`aks-bfhaks-ihub-eus2-dev-rst-01`) in the DEV environment. This caused multiple problems that forced us to abandon that approach.

**Same RG restore (RST cluster in DEV) what went wrong:**

When the RST cluster shared the same resource group as DEV (`rg-bfhaks-ihub-eus2-dev-01`), Azure Backup restored all resources including Prometheus alert rule groups into that same RG. Since these rule groups are also managed by Terraform and have identical names, Terraform tried to create them again on the next pipeline run and Azure rejected it with `resource already exists` error breaking the shared DEV pipeline and affecting other teams' deployments.

Additionally every restored pod got stuck in Init state due to Workload Identity OIDC issuer mismatch. Each AKS cluster has a unique OIDC issuer URL and the Managed Identity federated credentials only covered the original DEV cluster's issuer. Managing all of this through the shared DEV Terraform pipeline was too complex and risky for a shared environment.

**Different RG restore (POC-02) why it works:**

POC-02 has its own separate resource group (`rg-bfhaks-ihub-poc-eus2-dev-01`). When Azure Backup restores namespaces to POC-02, all restored resources land in that separate RG completely isolated from DEV Terraform managed resources. No naming conflicts, no pipeline breakage, no impact on other teams. The platform team has full access to POC-02 and it was already running so no new cluster provisioning was needed.

**Main technical challenge**

The Workload Identity OIDC issuer mismatch remains the key blocker regardless of which cluster is used as the restore target. After restore, pods get stuck in Init state because the Managed Identity federated credentials only cover the original cluster's OIDC issuer. I resolved this manually by adding federated credentials via the portal for each namespace. However with 71 namespaces this is not scalable.

I am currently researching automation options either a PowerShell script or Terraform approach to automatically create federated credentials for all namespaces in one run.
