Quick update on the AKS Workload Identity automation for the backup/restore flow.

In the previous PR, I implemented the `additional_clusters` approach, where the restore cluster was passed through the `TF_VAR_additional_clusters` variable. During testing, the pipeline was not picking up the additional cluster configuration as expected. The main issues appeared to be around how the complex `TF_VAR` value was being passed to Terraform, the Phase 2 local execution mode, and the pipeline potentially using an older build artifact. As a result, Terraform was evaluating `additional_clusters` as empty and no additional federated credentials were created.

Previous PR: [Previous PR Link]

I have updated the approach in the new PR so that the restore target is derived directly from the environment configuration. For example: `DEV → POC-02`

Terraform now detects the current environment from `conf.yaml`, maps it to the restore target, queries the target AKS cluster for its OIDC issuer URL, and passes that information to the `kubernetes_resources` module to create the required federated credentials.

New PR: [New PR Link] 

Please take a look when you have a minute. This removes the dependency on passing the complex cluster configuration through `TF_VAR_*` and should make the restore mapping more deterministic. The same approach can also be extended later for SIT/UAT/PERF and DR clusters.

I think this approach is more deterministic and maintainable. Ready to apply to the pipeline and test the restore flow once you sign off. Thoughts?
