Hey team, wanted to give a quick update on the AKS backup/restore issue since I know there's some confusion about what actually caused what.

So when I set up the dev-rst cluster (the restore/validation cluster from Azure Backup), it started causing an RBAC issue on the original dev cluster, role assignments and federated credentials were getting messed up because the pipeline was treating the restore cluster like it needed its own full run, and it ended up fighting with the original cluster over the same Terraform state. Basically every time it ran, it would touch the original cluster's stuff too. I dug into it, found the root cause, and fixed it the same day. Now the original cluster runs completely untouched like before, and the restore cluster just gets the one extra credential it actually needs to authenticate its restored pods, nothing else gets recreated or touched. I also fixed the alert naming so the two clusters don't clash on alert names either. This part was genuinely caused by the backup/restore setup, and it's sorted now.

But after that, I was working with the applications team and ran into a few more issues that people are assuming are also because of AKS backup, but they're actually unrelated. First one was apps using the wrong SQL DB in every environment, so I corrected them to point to the right DB. Then some pods weren't coming up in a few namespaces, turned out the SIT configmap had wrong values, I told the dev, he updated it and it started working. Then yesterday same environment had another issue, this time it was a wrong port being used, I told him to fix it and it worked right after.

So just to be clear, only the RBAC thing was actually caused by the backup setup, and that's fixed. The SQL DB, configmap, and port issues were just pre-existing app-level misconfigurations that happened to surface around the same time, nothing to do with AKS backup itself.
